# BSP-InventorySync API for other mods

Package `com.mrgregles.bsp_inventorysync.api`. Compile against the BSP-InventorySync jar from `build/libs/` (ForgeGradle: a `flatDir` repository and `compileOnly fg.deobf("blank:bsp-inventorysync:<version>")`); keep every call in one adapter class on your side and reach it only when `bsp_inventorysync` is loaded. These classes are the only ones meant for other mods; anything else in the jar may change without notice.

`InventorySyncApi.API_VERSION` is `2` (2 added `read`, `edit`, `saveNow`, `graves`, `graveItems` and `returnGrave`, below). It is a compile-time constant, so catch `LinkageError` to detect an older BSP-InventorySync.

| Call | What |
|---|---|
| `InventorySyncApi.registerModule(DataModule)` | Adds your per-player data to every snapshot. Implement `DataModule`: `id()` (letters, digits, underscores), `save(ServerPlayer, CompoundTag out)`, `load(ServerPlayer, CompoundTag in)`. Both run on the server thread; a module that throws is logged and skipped while the rest still run. Register during common setup. |
| `InventorySyncApi.excludeItems(Predicate<ItemStack>)` | Items matching the rule are never written into a snapshot; their slot is saved empty. BSP-Core's live Shatter Totem rule is installed this way by BSP-InventorySync itself. |
| `InventorySyncApi.isSyncing(UUID)` | Whether the player's data is still arriving (between login and the restore, or the timeout fallback). The player is frozen while true: no movement, interaction, pickup, drop, block breaking or damage. Treat the inventory as not yet theirs. |
| `InventorySyncApi.isEnabled()` | Whether this server syncs at all (`storage.mode` is `mysql`). |
| `InventorySyncApi.beginTransfer(ServerPlayer, String targetServer)` | For a teleport mod about to send the player to another server: call it after BSP-Core's `BspTransfer.beginTransfer` and before the proxy switch. Takes a snapshot now, so the save is in flight when the player leaves; the logout saves once more, marked as a transfer. Returns false when sync is off here or the player's own data is still arriving. |
| `InventorySyncApi.cancelTransfer(ServerPlayer)` | The announced transfer did not happen; the next logout is an ordinary one. |
| `InventorySyncApi.read(UUID)` | API 2. A player's items for a staff tool, live or from their newest snapshot: `CompletableFuture<Optional<PlayerItems>>`. See "Staff tools". |
| `InventorySyncApi.edit(UUID, long expectedVersion, Edit, String by)` | API 2. One change to a player's items, live or on their newest snapshot: `CompletableFuture<EditResult>`. See "Staff tools". |
| `InventorySyncApi.graves(UUID)` | API 2. A player's graves that still hold something, newest first: `CompletableFuture<List<GraveInfo>>` (id, short id, server, place, placed, put away, times, stacks, XP, `recoverable` by the player with `/grave`, `returnable` by an admin: not placed, or put away). Callable from any thread; completes on the server thread; fails when graves are off here. |
| `InventorySyncApi.graveItems(UUID, String id)` | API 2 (Server Utilities' request SU-IS3). What one grave holds, what a return would give back: `CompletableFuture<Optional<GraveItems>>`, `areas` and `xp`. The area `grave` (kind `GRAVE`) has one slot per stack, as copies with all their data, `missingItem` and `locked` as in `read` (a Shatter Totem as an inert copy); then a `backpack/<contentsUuid>` or `dank/<frequency>` area for each backpack and dank inside it, with its `place` (area `grave`, the slot, the containers in between; a backpack inside another backpack sits in that one's area). Only backpacks and danks whose item is still in the grave are listed (stored contents of one already taken are not). Their contents are as the grave stored them at the death: a return on another server gives exactly these; on the server where the player died it gives what that server's storage holds then, which differs only if a duplicated backpack or another dank on the same frequency changed it since. A slot holding a live totem, or an item carrying one anywhere inside (a shulker box, a backpack's stored contents), is locked and its copy holds only inert husks; this holds for `read` too. Every area is read-only (`addable` and `removable` false), and an `edit` aimed at `grave` is refused. Empty when they have no grave with that id (its id or first eight characters) or it has been emptied. Network-wide when the sync is on, as `graves`. Nothing changes, nothing is logged. Callable from any thread; completes on the server thread; fails when graves are off here. |
| `InventorySyncApi.returnGrave(UUID, String id, String by)` | API 2. Returns a grave to its owner as `/invsync grave return` does: `CompletableFuture<GraveReturn>`, outcome `OK`, `PARTIAL` (`left` stacks wait for them, maybe all of them), `QUEUED` (offline or still arriving: at their next arrival), `ONLINE` (`serverId`: return it there), `BUSY` (the grave changed or is being saved, or the player is not alive: try again), `NOT_FOUND`, `REFUSED` (a standing headstone), `FAILED` (also a login refused here); with a line for staff and the stacks returned and left and the XP. `ok()` is true for `OK`, `PARTIAL` and `QUEUED`. `id` is the grave's id or its first eight characters; `by` is logged as "panel: <by>" ("staff" when blank). Callable from any thread; completes on the server thread. |
| `InventorySyncApi.saveNow(ServerPlayer)` | API 2. Saves a player of this server now, as an admin snapshot: `CompletableFuture<Long>`, the new version, or 0 when the sync is off here or their data is still arriving (nothing saved). Server thread. |

## Staff tools: reading and changing a player's items (API 2)

Built for Server Utilities' staff web panel (its request SU-IS2; decisions D29 here and its audit, D256 and D257 there). Nothing here kicks, freezes or teleports anyone.

**Threads.** `read` and `edit` may be called from any thread; `saveNow` on the server thread. All three futures complete on the server thread. Never `join()` or `get()` them on the server thread: the answer needs the server thread (and often the database), so that would hang the server. Use `thenAccept` and friends. `read` and `saveNow` fail (complete exceptionally) when the store fails or when no server is running; `edit` answers `FAILED` with the reason instead, except when no server is running.

**Where the player is decides what happens.** The server that holds the player (their checkout) is the only one that changes them; a panel sends the request to its agent on that server.

| The player is | `read` gives | `edit` does |
|---|---|---|
| on this server, data arrived | live data (`live` true), with `version` the newest snapshot's | the change live; `expectedVersion` is not used (the slot is checked instead); the state before is saved and pinned, the change saved as an `admin` snapshot noted "panel: <by>"; answers with both versions |
| on this server, data still arriving | the newest snapshot (`live` false, `online` true) | `BUSY` |
| on this server, login refused (their data could not be read or applied) | the newest snapshot | `FAILED`, with the reason |
| online on another server | the newest snapshot, up to one auto-save old (`online` true, `serverId` that server) | `ONLINE`, `serverId` that server; nothing changed |
| offline | the newest snapshot (`serverId` the last server) | the change on that snapshot, only while it is still `expectedVersion`; the same steps as `/invsync edit` offline: one change at a time per player on this server, the checkout claimed while writing, the change saved as an `admin` snapshot noted "panel: <by>" under the server id of the snapshot it changes (a dank's frequency belongs to that server, so the restore renumbers it correctly), the version it started from pinned; they get it at their next login on any server |
| unknown (never saved), or the sync is off here and they are not here | empty | `FAILED` |

**`PlayerItems`**: `player`, `online`, `serverId` (empty when the sync is off here), `live`, `version` (pass it to `edit` for an offline player; 0 when there is no snapshot), `savedAt`, `areas` (a list of `ItemArea`; `area(id)` finds one).

**`ItemArea`**: `id`, `kind`, `addable`, `removable`, `place`, `slots` (slot `i` is `slots().get(i)`, empty ones included), `size()`, `slot(i)`, `key()`. The areas, in this order (a section the snapshot lacks because it failed to save has no area):

| id | kind | slots | `edit` may add | may remove |
|---|---|---|---|---|
| `inventory` | `INVENTORY` | 36: 0 to 8 the hotbar, 9 to 35 the rest | yes | yes |
| `armor` | `ARMOR` | 4: 0 feet, 1 legs, 2 chest, 3 head | no | yes |
| `offhand` | `OFFHAND` | 1 | no | yes |
| `cursor` | `CURSOR` | 1 (the item held on the mouse in an open screen) | no | yes |
| `ender_chest` | `ENDER_CHEST` | 27 in vanilla | yes | yes |
| `curios/<type>`, `curios_cosmetic/<type>` | `CURIOS`, `CURIOS_COSMETIC` | one Curios slot type (`ring`, `back`, ...); the cosmetic row only when the type has one; `key()` is the type | no | yes |
| `backpack/<contentsUuid>` | `BACKPACK` | a Sophisticated Backpack's item slots (not its upgrades or settings); `key()` is the contents id; a backpack never opened has 0 slots (its contents do not exist yet) | live only | yes, except a linked-storage backpack (read-only: its items live in another backpack) |
| `dank/<frequency>` | `DANK` | a Dank Storage dank's slots (9 to 81 by tier); `key()` is its frequency on the server the data comes from | live only | yes |

In a snapshot a backpack's filters, memorised slots and stack upgrades and a dank's tier limit are not stored, so offline they only give items up. Backpacks are every backpack the snapshot carries: in the inventory, on the cursor, in the ender chest, in a Curios slot, inside a shulker box or any other item, and inside other backpacks. Danks are those in the inventory, ender chest and cursor (as the sync saves them).

**`ItemPlace`** (`place` of a backpack or dank area): `area` and `slot` of the slot holding it, and `inside`, the item ids of the containers in between, outermost first. In the ender chest: `ender_chest`, 2, `[]`. Inside a shulker box in inventory slot 7: `inventory`, 7, `[minecraft:shulker_box]`. Inside another backpack: `backpack/<that one's id>`, its slot, `[]`. Null when the backpack's item was not found among the player's items.

**`ItemSlot`**: `index`, `stack` (a copy; backpack and dank counts above 64 are real), `missingItem` (the item's id when its mod is missing on the server that read it: `stack` is then this mod's placeholder barrier, which keeps the real item and may be removed like any other; null otherwise), `locked` (a live Shatter Totem, or an item holding one anywhere inside: `stack` is then a copy in which every such totem is an inert spent husk; show it locked, and never place or give it).

**`Edit`**, one change per call:
- `Edit.add(area, stack)`: puts `stack.getCount()` of the item into an addable area, first onto stacks of the same item and tags, then into empty slots in order; all of it or nothing (`NO_ROOM`). Live, a backpack takes what its own rules allow (filters, memorised slots, stack upgrades; nothing is voided) and a dank what its tier, its locked slots and its blacklist allow. Refused (`REFUSED`) for a Shatter Totem anywhere in the item (a shulker box holding one), an item carrying a backpack's or dank's contents id or a storage link (two items would share one inventory; add an empty one), an item no snapshot carries, a missing mod's placeholder, more than 100 stacks' worth (as `/invsync give`), and for areas that only give items up.
- `Edit.remove(area, slot, expected, count)`: takes `count` from one slot, which must still hold `expected` (the same item and tags as the read showed; the count is not compared) with at least `count` of it; otherwise `CHANGED`. Refused when the slot's item is or holds a live Shatter Totem (inside it, or in a backpack it is or holds), and in a linked-storage backpack.

**`EditResult`**: `outcome`, `message` (one plain line for staff), `version` (the snapshot the change was saved as; 0 when it could not be saved yet, and then it is saved with the player's next save; also 0 with the sync off here, where this mod saves nothing), `pinnedVersion` (the state before, pinned: `/invsync restore <player> <version>` undoes the change while they are online; 0 when it could not be saved or pinned, which the message says), `serverId` (`ONLINE`: the server holding them; otherwise this one), `ok()`. Nothing was changed unless the outcome is `OK`.

| Outcome | Meaning |
|---|---|
| `OK` | done |
| `ONLINE` | online on `serverId`: make the change there |
| `CHANGED` | the data moved since it was read: a newer snapshot, the slot no longer holds the expected item, or the area is gone. Read again |
| `BUSY` | try again in a moment: their data is arriving here, or this server is saving them (a logout save on its way) or writing another change of theirs |
| `NO_ROOM` | the add did not fit |
| `REFUSED` | not allowed (see `Edit`) |
| `FAILED` | anything else: no saved data, no such area or slot, a count below 1, a section their snapshot lacks, a login refused here, the sync off for an offline player, the server stopping, the database failing or not answering in time |

**Changes made some other way.** A live change to a player's inventory, ender chest, Curios slots, backpacks or danks, by any mod, is caught by the next save: the auto-save (every `storage.autosaveSeconds`, 60 by default) captures all of it and writes when anything differs, and every logout, transfer, death and world save captures it too. Between auto-saves a crash loses it; `saveNow(player)` closes that window.

**Each panel change** writes one log line on the server that made it, `panel: <by> changed <player>'s items ...` with the change; the note "panel: <by>" is kept inside the snapshot (`Note` in the snapshot format; `/invsync snapshots` shows the cause `admin` and, for an offline change, the server of the snapshot it changed). A blank `by` is noted as "staff".

**Known limits** (left as they are, D29 audit): a backpack never opened reads as 0 slots; server ids that differ only by case are the same server (as `sync.networkServers` already treats them, and as Server Utilities does); once an arrival's wait times out (`arrival.timeoutSeconds`), it takes the checkout whatever holds it, so an offline change still being written at that moment can be read past and lost. The stored formats were read from the servers' jars (Curios 5.14.1, Sophisticated Core 1.5.12 with Sophisticated Backpacks 3.26.12, Dank Storage 16) and from the newer ones in the pack folder (Sophisticated Core 1.5.24, Backpacks 3.26.19), which store them the same way.

## Events

Package `com.mrgregles.bsp_inventorysync.api.event`, posted on `MinecraftForge.EVENT_BUS` on the server thread; notifications only, never cancelable.

| Event | When | Carries |
|---|---|---|
| `InventoryRestoredEvent` (a `PlayerEvent`) | once per restore on this server, after every data module has run and after any Shatter Totem the player held before the restore has been given back through BSP-Core. Also fires with version 0 when the player had no snapshot (a first login) and when the sync is off on this server, so listeners can always rely on exactly one per login. It also fires with version 0 when the player's only snapshots come from servers outside `sync.networkServers` (skipped), and with the failed modules listed when some modules failed. None fires for a login that ends before the restore (the player left, was refused at the timeout, was refused because their data could not be read, or the restore itself failed outside the data modules): the player is disconnected, and a listener waiting for them should drop the wait at their logout. A listener that throws is logged; the login and the other listeners go on. | `getEntity()` the `ServerPlayer`; `getVersion()` the snapshot's per-player version (0 = none); `getSourceServer()` the saving server's id; `isFallback()` true when the arrival wait timed out and the last known snapshot was applied; `getFailedModules()`; `getTotemsKept()` |
| `InventorySavedEvent` | once the shared store confirms a snapshot was written; may be after the player left | `getPlayer()` uuid, `getPlayerName()`, `getCause()` (`SaveCause`: logout, transfer, death, autosave, world_save, admin), `getVersion()`, `getBytes()`, `getServerId()` |

**BSP-Core** (request R3, built in BSP-Core 1.4.1): with this mod loaded, a login holds the coin strip for an older season, the season check and owed items until `InventoryRestoredEvent`, because they touch the inventory and saved data the restore replaces; its start-up log says "Coins, the season check and owed items wait for BSP-InventorySync's restore event at login". If no event comes within its `storage.restoreWaitSeconds` (30), it settles by itself. A player who arrives dead gets their data, and the event, at the respawn, on the respawned entity; BSP-Core (request R4) never settles on a dead player, its countdown stands still on the death screen and restarts at the respawn. From BSP-Core 1.4.2 (request R5) a totem it holds for a player meanwhile is handed over through its totem route (ledger arrival, never dropped); use 1.4.2 or later with this mod, since on 1.4.1 such a totem can be dropped or spent. With BSP-Core 1.4.1 or later the totem rule and hand-back use its api (`BspTotems.isTotem(ItemStack)`, `BspTotems.giveBack(ServerPlayer, ItemStack)`, requests R1 and R2); older versions are reached through its internal methods.

## The arrival handshake

A server switch is a logout on the source and a login on the target within the same second. The shared store's presence row is the checkout: a server marks a player online on itself once it has applied their data, and offline only after its last save of them has landed. The target freezes the arriving player and polls the row every tick; the moment the source has released them it takes the row, reads the newest snapshot and applies it. Taking the row is one step in the store (`SyncStore.claim`: taken only when nobody else holds it, D29), so a change written to an offline player from another server at that same moment (`/invsync edit` offline, the staff panel) is never read past: the arrival waits for that server's release, then reads the snapshot with the change. A server writing such a change also makes an arrival of that player on itself wait. If the source has not released them within `arrival.timeoutSeconds` (10), the last known snapshot is applied and the player told it may be out of date (`arrival.kickOnTimeout = false`), or the login is refused so they can try again (`true`). A player who leaves before the restore is never saved. A player who arrives dead gets their data at the respawn. The login listener runs at `EventPriority.LOWEST` so BSP-Teleport's landing has happened first; the logout listener at `LOWEST` so BSP-Core has taken the carried totems first.

## What BSP-InventorySync never syncs

A live Shatter Totem (`bsp_core:shatter_totem` without the `Spent` flag): BSP-Core places or stores it itself when the player leaves. A totem found on the player at restore time (handed back by BSP-Core a few ticks after login) is kept and put back through BSP-Core's own hand-back, never dropped. Statistics and the recipe book are not synced (design decision D3).

## Operator commands

`/invsync` (permission level 2): `status` (server id, store and Redis state, counters, modules, totem rule source, a store ping), `reload` (config re-read, stores reopened, online players adopted), `save <player>`, `resync <player>` (apply the newest snapshot again), `dump <player>` (per-module sizes; the full SNBT goes to `world/bsp_inventorysync/dumps/`), `snapshots <player>` (newest first: version, cause, server, age, size, pin), `restore <player> <version>` (a rollback, player online), `pin` / `unpin <player> <version>` (rotation never removes a pinned snapshot).

`/invsync give <player> <item> [count]` (permission level 2, and the console) gives an item on any server of the network: the item as vanilla `/give` takes it, at most 100 stacks' worth, Shatter Totems and items no snapshot carries refused. What fits goes in at once when the player is on that server and their data has arrived; the rest waits in the store (`SyncStore.addGive`, `gives`, `takeGive`; table `bsp_is_gives`), one row per stack, and the server the player is on hands it over every `give.pollSeconds` and at each arrival, after the restore and its event. A row is removed before its stack is handed over, so it is handed over once. Stacks that do not fit are shown in a three-row chest popup (Deposit, Cancel); a Cancel is kept in the extra blob `give_declined` until the player's next join (an arrival whose snapshot was not saved as a transfer). With the sync off the same rules run on an in-memory store for that server only.

`/invsync edit <player> [word]` (permission level 3) opens the inventory editor for a player online on the same server, or on the newest snapshot of a player who is offline (refused for a player online on another server): a chest screen with Inventory (main, hotbar, armour, offhand), Ender chest and Items tabs over a toolbar (Trash, Cancel, Save). Items come from a creative list (by creative tab, or filtered by the word); nothing changes until Save, then Confirm. Confirm is refused if the player's inventory changed meanwhile (offline: if they came online, or a newer snapshot was saved); with the sync on, the state before is saved (offline: the snapshot it started from) and pinned, and the edit saved as an `admin` snapshot. An offline edit claims the player's checkout before it checks the version and holds it while it writes (D29), so a server they join at that moment, this one included, waits for it; it waits for another change of theirs being written on this server and for this server's own save of them, and is saved under the server id of the snapshot it changes (so that server's dank frequencies are renumbered wherever else it is restored). The admin's own inventory is locked, and whatever is on the cursor when the screen closes is dropped. Shatter Totems the player holds can be trashed; the list never offers one. An admin in spectator mode is refused, and an open editor closes (nothing changed) when its admin turns spectator: Minecraft ignores a spectator's clicks in every inventory screen, so the editor would show but never respond.

`/grave` (every player) lists the player's graves on every server, newest first, each with where it is, how old it is and how many stacks it holds; a grave that found no spot, or that nobody opened for `graves.recoverAfterDays` (7), has a [Recover] link that runs `/grave recover <id>` and opens its screen wherever the player is. Put-away graves are not listed.

`/invsync graves <player>` (permission level 2, and the console) lists every grave of a player, put-away ones too, newest first, each with its id (the first eight characters of its UUID). The other admin commands take that id, never a place in the list, so a grave made or emptied in between never changes what they act on. `/invsync grave open <player> <id>` opens that grave's screen for the admin (any age; what they take goes into their own inventory). `/invsync grave give <player> <id> <to>` makes the grave `to`'s, in one write: no block any more, recovered by them with `/grave` at once, its contents (backpacks and danks included) and XP with it; it can only happen once. `/invsync grave remove <player> <id>` empties it for good, with a log line listing every stack. The grave's block goes when it stands on this server (elsewhere at the next right-click), and the owner is told. `/invsync grave return <player> <id>` (D30 and its audit) puts a grave that could not be placed, or one put away, back into its owner's inventory, as [Recover] and Take all do: each stack to the slot it came from when that is free (armour worn again), else into the inventory, backpack and dank contents with it, and the grave's XP to them. The grave is written first and only then handed over, so nothing comes twice. What does not fit stays in the grave, recoverable with `/grave` (a put-away grave is brought back with no block for it, even when nothing fits); stacks that could not be handed over after all (the inventory changed, or the player left) go into a new grave of theirs, with the XP if they left, and the answer names it. The player gets it at once when they are on the server running the command and their data has settled (they are then saved at once), at their next arrival on any server when they are offline or still arriving (the grave itself is marked, at its revision, so two admins or a delivery never race; a hint in the extra blob `grave_return` makes each server's minute round look too; an arrival always looks), and it is refused for a player online on another server (run it there) and for one whose login here was refused. A standing headstone is opened where it stands, even when its block is missing (the owner already recovers such a grave with `/grave`). The player is told; one log line names who returned what: the admin's name from the command, "panel: <by>" from the api ("staff" when `by` is blank).

**LuckPerms.** The servers' LuckPerms Forge gives every command a node, `command.<the words of the command>` (literal words only). Set to true it allows that command as if the player were an operator for it; set to false it hides it; unset, the command's own rule applies. `/grave` has no rule of its own (every player), so it only needs granting where a group denies `command.*`: `command.grave` and `command.grave.recover`. The grave commands' nodes: `command.grave`, `command.grave.recover`; `command.invsync`, `command.invsync.graves`, `command.invsync.grave`, `command.invsync.grave.open`, `command.invsync.grave.give`, `command.invsync.grave.remove`, `command.invsync.grave.return`. Every `/invsync` subcommand except `edit` has no rule of its own (only `/invsync` itself asks for operator level 2), so **setting `command.invsync` true opens all of them** to that player when their nodes are unset: `status`, `reload`, `save`, `resync`, `restore`, `give`, the grave commands and the rest; `edit` also needs `command.invsync.edit` (it asks for level 3). To give a staff group only some of them, set `command.invsync` true and the others false, for example `command.invsync.reload`, `command.invsync.restore` and `command.invsync.give` false; a subcommand set false is hidden from them. Where a group denies `command.*`, every node under it is false too: then each command and each of its words must be set true, for example `command.invsync`, `command.invsync.grave` and `command.invsync.grave.return` for the return alone.

Graves live in the table `bsp_is_graves` (`GraveStore` in `storage/`, part of `SyncStore`), or in the world's `data/bsp_inventorysync_graves.dat` on a server without the network database. On a synced server a new grave is written together with the owner's next snapshot (`SyncStore.saveWithGraves`, one transaction), so the grave and the empty-handed inventory land together or not at all; until then the grave is held by the server where the player died (`sync/GraveCarrier`) and cannot be opened; if that player's logout save fails, the grave is dropped (the database still has them as before the death, items included). Every change is made at the revision read; an error is checked by reading the grave back. An emptied grave stays as a marker (no stacks, no XP) until the sweep removes it, so an old copy sent again finds its id taken. Every server puts away graves nobody opened for `graves.archiveAfterDays` (30), deletes put-away ones `graves.deleteArchivedAfterDays` (30) later, and removes emptied markers after the same time. Notices for an owner who is on another server wait in the extra blob `grave_notice` until a server they are on hands them over (within a minute).

## Compact Machines: a bound machine works only on its home server (D31)

Compact Machines 6.0.3 names a bound machine's room by its chunk position alone (the int array `room_pos` in the item's tag), and every server numbers its rooms in the same order, so a machine carried to another server would open that server's room at the same position, perhaps another player's. This mod marks each bound machine item (`compactmachines:machine_tiny`, `_small`, `_normal`, `_large`, `_giant`, `_maximum` with `room_pos`) with the server its room is on: the string `bsp_inventorysync:home` in the item's tag, holding the server id (`storage.serverId`). Compact Machines' own tags are never changed; unbound machines (no `room_pos`) are never marked and work everywhere; nothing is wiped.

- **Marked** with this server's id, only on a server where Compact Machines is installed (a server without it holds no room): in every snapshot it saves (inventory, armour, offhand, ender chest, Curios, Sophisticated Backpack and Dank Storage contents, and items inside items at any depth: shulker boxes, bundles); a machine dropped as an item there (the machine block's own drop); a grave's contents at the death; a machine given with `/invsync give` (the giving server, wherever the row is delivered). When a snapshot is applied, a machine still unmarked takes the server that saved the snapshot; a grave stored before the mark gives its machines the grave's server when it is read. A mark is never changed except by the command below.
- **Unmarked** bound machines count as local (D31 5 a): a machine moved before this version, or one that reached a player without passing through a save, a drop or a give (a creative pick-block, a machine broken straight into an inventory by a tool), is marked by the next server that saves it.
- **Refused away from home**: a machine marked for another server (ids compared ignoring case) is never placed there. The check sits at the start of vanilla `BlockItem.place` (this mod's one mixin, `mixins.bsp_inventorysync.json`), which every placement of a block item goes through whoever places it: a player's click, Dank Storage's construction mode (it uses the selected item directly, so no event sees the machine), a Create deployer, another mod, a placer with no player. Nothing is set, so Compact Machines never binds the block. A player's right click with such a machine is also denied at the lowest priority (so no other mod's listener can allow it again), the clicked block still works (a chest opens), and the hand's slot is sent again so the client's own prediction is corrected. The player reads "This Compact Machine's room is on <server>. It only works there." on the action bar, at most once a second; a placer that is not a player is logged instead. A machine is refused the moment someone tries to place it wherever it was carried, inside containers this mod cannot read too, provided it was marked before it left. With the sync off (single player, no server id) nothing is refused.
- **Tooltip**: a marked machine shows one grey line, "Room on <server>".
- **`/invsync machine`** (permission level 2, a player): shows the home of the Compact Machine in the main hand. `/invsync machine home <server>` sets it (a renamed server, a mistake); an id that is neither this server nor in `sync.networkServers` is still set, with a warning, since a misspelt id makes the machine refused everywhere until it is set again. `/invsync machine clear` removes it: the machine then counts as this server's, the next save here marks it so, and placed here it opens this server's room at its position, not the one it came from; use it only on the machine's own server. Each change is logged.
- **The Personal Shrinking Device's way back** (capability `compactmachines:room_history`) names places on one server only, so it is in the default `sync.excludeCapabilities`. A server config written before this version keeps its own list: add the id there by hand.
- Not yet: the warning before a cross-server teleport with such a machine (D31's confirm screen; it needs BSP-Teleport's request T2).

## What travels besides the vanilla data

The `forge` module carries the player's persistent NBT (`ForgeData`) and capabilities (`ForgeCaps`), so a mod's per-player data needs no adapter unless it lives outside the player (world saved data). Paths and capability ids listed in the server config (`sync.excludeForgeData`, `sync.excludeCapabilities`) are neither saved nor overwritten; BSP-Core's `PlayerPersisted.bsp_core:LastMainDim`, `LastMainPos`, `LastMainServer` and `ZoneHeldTotems` are always excluded, whatever the list says; the defaults also exclude the Curios inventory (carried by the Curios adapter instead) and Compact Machines' `compactmachines:room_history` (places on one server). Adapters exist for Curios, Sophisticated Backpacks (contents by `contentsUuid`) and Dank Storage (contents by frequency, remapped on arrival from another server); each registers only when its mod is loaded. A mod whose per-player data lives in world saved data should register a `DataModule` of its own.

## Snapshot format

One GZIP-compressed NBT compound per snapshot: `{Format: 1, Modules: {<module id>: {...}}, Failed: [<module ids that threw on save>], Note: "<who made an admin change>"}` (`Note` only on snapshots of a staff panel change, "panel: <by>"; it is not player data). Module ids: `inventory`, `ender_chest`, `experience`, `game`, `vitals`, `advancements`, `forge`, and when loaded `curios`, `backpacks`, `dank`. An item whose id is not registered on the restoring server becomes a placeholder (a barrier named "Missing item: <id>"; paper before D14, still recognised) carrying the original compound in the tag `bsp_inventorysync:original`; it turns back into the item when saved again and restored where the item exists.
